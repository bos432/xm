# 历史归集批次保护

## 问题

生产公开首页当时唯一有效的开放批次是 `HISTORY-DEFAULT`。该批次明确用于迁移前历史项目归集，却被开放批次 API 和新项目批次解析器当作普通申报批次。这样可能导致新项目误绑历史归集批次；旧批次的宽泛起止时间也让它长期显示可用。

## 处理

- 新建/提交可用批次查询排除固定系统编号 `HISTORY-DEFAULT`。
- 公开门户批次列表不再将其列为可申报批次。
- 保留历史项目与该批次的外键关系和只读历史展示，不批量迁移、不删除历史数据。
- 管理 API 阻止改名、编辑或变更该系统批次状态，避免把保留记录改造成业务批次。
- 如果数据库只有该历史批次，单位端将没有可申报批次；管理员应先创建并配置实际业务批次，再开放申报。

## 验证

- 相关 Feature suites：37 tests、206 assertions，通过。
- PHP 语法检查：8 个变更 PHP 文件全部通过。
- 全量后端 suite：205 tests 中 203 通过、2 失败。两项既有失败分别涉及 API 未认证时 `Route [login] not defined` 和 `/up` 响应缺少安全头，与批次代码无关；全量 suite 使用的是版本匹配但来自另一工作区 commit 的 vendor bootstrap，因此需在 CI/干净依赖安装后复验。
- Pint：新增测试文件无格式问题；4 个已有应用文件在项目当前 Pint 规则下仍报告格式差异，本分支避免引入大范围无关格式重写。

## 发布约束

本改动尚未部署。生产上线前必须由业务负责人确定真实申报年度、起止日期、允许类别/类型、指南和必传附件，并由超管建立正式业务批次。部署后应验证公开首页只显示正式批次、单位能创建并提交到该批次、历史项目仍可读取。该修复不归档或删除现有 E2E 数据。
